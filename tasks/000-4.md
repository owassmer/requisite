# 000-4 Change one input, see exactly what changes: the incremental computation runtime

## Why
Every consequence Requisite shows (exposure, materiality, dated cash flows, payoffs, the optimizer's inputs) is computed
by registered pure nodes from committed state (spec I7). When one input changes (a judgment, an assumption, the planning
horizon), the runtime recomputes only what depends on it, stops where a recomputed value is unchanged, and emits a diff
of exactly the nodes whose values changed, old and new, grouped by layer (spec §5). That diff is the demo's fifth beat
(spec §15, outcome 006: "move the planning horizon; the diff shows exactly the exposure and optimizer nodes that
changed") and is never cut (spec §13). The addendum adds that a value unchanged by a new justification still changed
its lineage: a new source supporting the same number keeps cached arithmetic but must not silently keep stale approvals
or explanations (A11 §11.2).

## What to build
In `requisite/compute/runtime.py`: a graph of node instances over the registered nodes, each instance naming its node
(id and version), its inputs (other instances, or source values: committed records such as claims, judgments,
assumptions, parameters), and its layer (evidence, proposition, computation, contract: spec §5's four).
- Keys (spec §5): an output is keyed by node id, node version and its inputs' value hashes; a judgment-derived input adds
  its question version, state hash and judge configuration. A value hash is the canonical hash of the value; a lineage
  hash also covers each input's lineage, the node's version and the source records' identities, so it changes with
  provenance, a policy, a gold label, a provider version or a dependency edge even when the value does not (A11 §11.2).
- Recompute: given changed sources, recompute dirty instances in topological order; where a recomputed value hash is
  unchanged, its dependents stay clean (early cutoff) unless their own lineage changed, in which case their lineage and
  receipts update while their cached value stands. Nothing is recomputed that does not depend on a change.
- Diff: every recompute returns the instances whose value changed, with old and new values, grouped by layer, and
  separately the instances whose lineage changed with an unchanged value, and the approvals that no longer cover the
  current lineage (an Approval approves one lineage hash).
- Receipts: each computed value's DerivationReceipt (core), committed through the store, so a recompute is auditable.
- I7's static check: a node's function, and everything it imports from the product, reaches no provider, cassette or
  network code (an AST walk over the modules registered nodes live in, as tests/store/test_store.py walks for the
  database boundary).

## Done
Tests in `tests/compute/`, each marked with `@pytest.mark.covers(...)` for the registry items it is the one test for:
WP6.descendants (one changed input recomputes only its descendants, counted by calls), WP6.early_cutoff (an unchanged
value hash stops propagation), WP6.diff (exactly the changed nodes, old and new values, by layer), A.T20 (evidence
changes and the number does not: the cached value stands, and the provenance and approval change are visible in the
diff), I7 (the static check). Property tests (hypothesis) over random DAGs of pure nodes: an incremental recompute after
any change equals a from-scratch computation node for node, and the diff lists exactly the nodes whose value hash
differs between the two full computations (outcome 006's own check). `gates` passes; `uv run requisite registry` shows
the items covered.
